## 1. Project vision

The project is an **OSR-inspired sandbox RPG** built around a
persistent, simulated world.

The goal is not to build a huge map filled with scripted content. The
goal is to create a **relatively small but dense world** where systems,
factions, NPCs, events, and player actions interact in ways that can
produce emergent situations.

Core inspirations include the feeling and presentation of **Baldur's
Gate 1 / Baldur's Gate 2**, combined with a stronger emphasis on sandbox
simulation and world persistence.

The desired experience is closer to:

> "A world that continues to exist and react"

than:

> "A sequence of quests waiting for the player to activate them."

## 2. Core design principles

### 2.1 The world is not centered on the player

NPCs and factions should have their own goals, relationships, resources,
problems, and conflicts.

Events should be able to happen even when the player is not directly
involved.

The player can influence the simulation, but should not feel like the
only entity capable of causing change.

### 2.2 Persistent consequences

Important actions should modify world state.

Examples:

-   an NPC can die and remain dead;
-   a settlement can become weaker or stronger;
-   a faction can gain or lose territory or influence;
-   relationships between NPCs or factions can change;
-   an NPC can remember something the player did;
-   resources can be consumed, stolen, traded, or destroyed;
-   an event can create consequences that generate later events.

Persistence is a central part of the sandbox.

### 2.3 NPC agency

NPCs should not exist only as dialogue terminals or quest dispensers.

Important NPCs should be able to have:

-   goals;
-   needs;
-   relationships;
-   memories;
-   opinions;
-   current intentions;
-   knowledge that may differ from objective world state;
-   the ability to take actions without direct player involvement.

The exact implementation is still open and should emerge incrementally
from prototypes.

### 2.4 Factions as active systems

Factions are intended to be simulation participants rather than static
reputation meters.

Possible faction properties include:

-   objectives;
-   resources;
-   relationships with other factions;
-   controlled locations;
-   important members;
-   current plans;
-   threats;
-   reputation toward the player.

Faction actions should be able to affect NPCs, locations, and other
factions.

### 2.5 Small world, high density

Prefer a smaller world with meaningful interactions over a giant
procedural map.

A location should matter because of the people, factions, resources,
history, and events connected to it---not simply because it exists on
the map.

### 2.6 Emergent stories over scripted quest chains

Traditional authored quests can exist, but they should not be the only
source of gameplay.

The simulation should be capable of creating situations such as:

-   a merchant disappears because they were killed or kidnapped;
-   a faction loses access to a resource;
-   an NPC asks for help because of an event that actually happened;
-   a conflict escalates because previous events were not resolved;
-   the player returns to a location and discovers that the situation
    changed.

The desired result is **emergent narrative generated by interacting
systems**.

## 4. Presentation / aesthetic direction

The broad visual and interaction inspiration is the classic Infinity
Engine era, especially:

-   Baldur's Gate 1;
-   Baldur's Gate 2.

This does not mean reproducing those games mechanically or visually
one-to-one.

The relevant qualities are:

-   readable RPG presentation;
-   strong sense of place;
-   relatively compact areas;
-   exploration;
-   characters and encounters that make locations memorable.

## 5. Simulation model

The project should progressively develop a world simulation capable of
representing at least:

``` text
World
├── Time
├── Locations
├── NPCs
├── Factions
├── Relationships
├── Resources
├── Events
└── Player state
```

These systems should interact rather than remain isolated databases.

Example:

``` text
Faction needs food
        ↓
Faction attempts to secure farm
        ↓
Conflict with another faction
        ↓
NPCs are sent / injured / killed
        ↓
Location changes ownership
        ↓
Local prices / safety / dialogue change
        ↓
Player encounters the consequences
```

The important concept is the **causal chain**, not this specific
example.

------------------------------------------------------------------------

## 6. NPC memory and knowledge

One important idea is that NPCs should have some form of memory.

A useful distinction to preserve in the design is:

``` text
Objective world state
        ≠
What an NPC knows
        ≠
What an NPC believes
```

An NPC should not automatically know everything that exists in global
game state.

Potential memories could include:

-   interactions with the player;
-   witnessed events;
-   information received from another NPC;
-   promises;
-   threats;
-   crimes;
-   favors;
-   deaths;
-   changes in relationships.

Memory does not need to begin as a sophisticated AI system. Start with
simple explicit data structures and expand only when gameplay proves
that more complexity is useful.

## 7. Event-driven / event-sourced ideas explored

A possible architectural direction discussed previously is a generic
event-driven, potentially event-sourced core.

Conceptually:

``` text
Command / Action
      ↓
Validation
      ↓
World Event
      ↓
State changes
      ↓
Other systems react
```

Example events:

``` text
NpcMoved
NpcKilled
ItemTransferred
FactionRelationChanged
LocationCaptured
DialogueOccurred
CrimeWitnessed
TimeAdvanced
```

Benefits worth exploring:

-   easier persistence;
-   history of what happened in the world;
-   systems can react without being tightly coupled;
-   NPC memory can reference real events;
-   debugging the simulation becomes easier;
-   replay or reconstruction may become possible.

However, **event sourcing is not yet a final architectural commitment**.

Do not build a large generic event-sourcing framework before a concrete
gameplay prototype proves that it is useful.

------------------------------------------------------------------------

## 8. Content packs / data-driven content

Another idea explored is separating engine/simulation logic from game
content through loadable content packs.

Conceptually:

``` text
Engine
├── Simulation
├── Rules
├── Persistence
├── Event system
└── Behavior registry

Content Pack
├── NPC definitions
├── Factions
├── Locations
├── Items
├── Encounters
├── Dialogues
└── Behaviors / rules configuration
```

The long-term attraction of this approach is the possibility of reusing
the simulation engine with different worlds or rule sets.

This is still exploratory.

Avoid premature abstraction. A working game-specific implementation is
preferable to a theoretically generic engine that has no playable
sandbox.

------------------------------------------------------------------------

## 9. Behavior registry idea

A behavior registry was discussed as a possible mechanism for
associating data-defined entities or actions with executable C#
behavior.

Example concept:

``` text
"attack"        -> AttackBehavior
"trade"         -> TradeBehavior
"travel"        -> TravelBehavior
"steal"         -> StealBehavior
"investigate"   -> InvestigateBehavior
```

This could help keep content data-driven while retaining strongly typed
implementation code.

Treat this as an architectural option, not an established requirement.

------------------------------------------------------------------------

## 10. Dice and resolution

The project has explored supporting both:

-   automatic dice resolution;
-   manual dice input.

This is especially relevant if the engine is eventually usable in a
hybrid setup involving a human DM and players.

Possible abstraction:

``` csharp
public interface IDiceResolver
{
    RollResult Roll(RollRequest request);
}
```

Possible implementations:

``` text
AutomaticDiceResolver
ManualDiceResolver
```

This idea should remain decoupled from the core game logic so the
resolution method can change without rewriting gameplay systems.

------------------------------------------------------------------------

## 11. Hybrid DM + players possibility

A broader idea explored is that the underlying engine might eventually
support a **hybrid digital tabletop / RPG mode**, where:

-   the simulation manages persistent world state;
-   players interact with the world;
-   a human DM can intervene;
-   some rolls can be entered manually;
-   the DM may trigger or override events.

This is an interesting long-term direction, but it should **not expand
the initial scope**.

The first objective remains proving that the sandbox simulation is fun
and technically manageable.

------------------------------------------------------------------------

## 12. AI / LLM philosophy

NPC agency and memory do **not** imply that every NPC must be powered by
an LLM.

Prefer deterministic or inspectable game systems for core simulation.

LLMs may eventually be useful for areas such as:

-   dialogue realization;
-   transforming structured NPC intent into natural language;
-   summarizing memories;
-   assisting content creation.

But critical world state and game rules should remain represented by
explicit structured data.

Do not make the simulation dependent on an external LLM unless that
decision is explicitly revisited.

------------------------------------------------------------------------

## 13. Architecture philosophy

This project is intentionally exploratory.

Do **not** treat early architectural ideas as permanent commitments.

Preferred workflow:

``` text
Gameplay need
    ↓
Small implementation
    ↓
Playable experiment
    ↓
Observe problems
    ↓
Extract reusable abstraction
```

Avoid:

``` text
Imagine every future requirement
    ↓
Build generic framework
    ↓
Build another abstraction layer
    ↓
Eventually try to make a game
```

The project should evolve from concrete gameplay experiments.

## 14. Suggested initial vertical slice

A useful first sandbox prototype could contain:

-   one small settlement;
-   one nearby wilderness/location;
-   roughly 5--10 meaningful NPCs;
-   2 factions;
-   a few resources;
-   world time;
-   NPC movement/actions;
-   relationships;
-   a small event log;
-   save/load;
-   one conflict capable of evolving without the player.

Example scenario:

``` text
Village
├── Innkeeper
├── Farmer
├── Guard captain
├── Merchant
└── Hunter

Faction A: Village authority
Faction B: Local bandits

Resource: food

Bandits begin stealing food.
The village gradually loses supplies.
NPC behavior changes.
The guard captain reacts.
The merchant changes prices.
The farmer becomes increasingly threatened.

The player can:
- ignore the situation;
- help the village;
- help the bandits;
- exploit the shortage;
- kill important actors;
- create an unexpected outcome.

The simulation should continue regardless.
```

The purpose of the prototype is **not content quantity**. It is to prove
that a small number of systems can generate meaningful consequences.

## 16. Persistence

Persistence is a first-class requirement.

The save system will eventually need to preserve enough state that the
world genuinely continues from the previous session.

Likely categories include:

-   game time;
-   entity state;
-   NPC state;
-   faction state;
-   relationships;
-   locations;
-   inventories/resources;
-   important events;
-   NPC memories;
-   ongoing plans/actions.

The exact persistence strategy is not yet fixed.

Event sourcing is one candidate, but ordinary state snapshots plus an
event/history log may be simpler initially.

## 17. Debugging and observability

Because emergent simulation can become difficult to understand,
debugging tools should be considered part of the game architecture
rather than an afterthought.

Useful development tools may include:

``` text
World inspector
NPC inspector
Faction inspector
Event timeline
Relationship viewer
Time controls
Force event
Teleport entity
Advance simulation
Pause simulation
```

A crucial debugging question should always be answerable:

> Why did this NPC do this?

Whenever possible, AI decisions should expose their reasoning in
structured/debuggable form.

Example:

``` text
NPC: Arlen
Action: Leave village

Reasons:
+ Bandit threat: 70
+ Food shortage: 45
+ Family safety goal: 80
- Loyalty to village: 30

Selected action score: 165
```

This does not prescribe a specific AI algorithm; it describes the
desired observability.

------------------------------------------------------------------------

## 18. Development priorities

When deciding what to build next, prefer roughly this order:

1.  A playable interaction.
2.  A minimal simulation supporting that interaction.
3.  Persistence of its consequences.
4.  Debug visibility.
5.  Additional interactions between existing systems.
6.  More content.
7.  Generalization / reusable engine architecture.

Avoid prioritizing engine elegance over a working sandbox.

## 19. Instructions for coding assistants

When working on this repository:

### Always

-   Inspect the existing repository before proposing major architecture.
-   Prefer incremental changes.
-   Explain architectural trade-offs.
-   Keep domain logic separate from Godot presentation code where
    practical.
-   Keep simulation state serializable where practical.
-   Favor testable C# logic for simulation systems.
-   Preserve the possibility of deterministic simulation.
-   Add debugging/inspection support for complex autonomous behavior.
-   Treat this document as project context, not unquestionable
    specification.

### Avoid

-   Rewriting the project around a new architecture without explicit
    approval.
-   Introducing a large framework because it might be useful later.
-   Assuming every NPC needs complex AI.
-   Making LLM calls part of critical simulation logic.
-   Creating giant inheritance hierarchies before gameplay requires
    them.
-   Generating large amounts of procedural content before the core
    simulation works.
-   Treating factions, NPCs, or locations as static quest decorations.
-   Hard-coding world consequences directly into UI scenes.

### When uncertain

Prefer asking:

> "What is the smallest implementation that lets us test this gameplay
> idea?"

rather than:

> "What architecture could theoretically support every future version of
> this project?"
